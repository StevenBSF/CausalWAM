# Policy v2 实验规划（Release-base 主线）

> 本文件是 [`policy_protocol_v2.md`](policy_protocol_v2.md) 的实施顺序与 gate 规划。2026-08-19 起，当前主线使用作者发布的 RoboTwin 50-task checkpoint 作为固定共同基座；方法本身不变。原三任务 Stage 1 `B_CR` 训练及基于它的 C0/C1/C3 复验后移为独立扩展，不与 release-base 主结果混表。

## 0. 当前要回答的问题

在相同作者全任务预训练 FastWAM、相同三任务 official continuation、相同 Head/GCA、相同训练预算和相同 RoboTwin 在线评测下：

1. C/R1/R2/R3 的 paired contrastive supervision 是否提高 official Random success rate？
2. 提高 Random robustness 时是否保持 Clean success rate？

固定任务：

- `place_a2b_left`；
- `open_microwave`；
- `move_stapler_pad`。

当前唯一主因果比较是：

\[
\text{C3}-\text{C1}.
\]

这项比较估计的是“paired contrastive supervision 在作者全任务预训练策略上的增量作用”。当前不再要求重新运行 C0；若已有相同 final seed bank/rollout protocol 的完整原始 FastWAM 六格结果，C3−C0 才可作为可选整体适配参考。C2 普通 augmentation 后移为辅助对照。

### A2. 必须生成的 lineage

新增不可覆盖的 `author_release` base-lineage manifest，至少绑定：

- checkpoint/stats 路径、大小和 SHA-256；
- 作者 release 来源与模型配置；

- 三相机顺序、图像尺寸和预处理；
- action/state normalization；
- 50-task × 550 分区 manifest；
- 当前源码与 evaluator 版本。

C0/C1/C3 必须引用同一个 lineage。禁止为 C1/C3 重新计算三任务 stats 后静默改变基座语义，也禁止伪造 Stage 1 completion manifest 来冒充 release ancestry。

### A3. Gate

- checkpoint 和 stats SHA 与本文件一致；
- 模型严格加载且 key coverage 通过；
- 三个目标任务的 episode 范围与 official manifest 一致；
- 原生 C0 action path 可加载并执行；
- release-base config/audit 单元测试全部通过。

未通过 A-phase，不提取 cache、不启动 P-mode pilot 或正式 Stage 2。

## 2. Phase B：C0 原生在线基线（可选，不再阻塞）

C0 是固定 `B_release`，不做任何 Stage 2 训练：

- 优先直接使用作者原生 policy rollout；
- 若统一聚合器必须使用 transport checkpoint，只允许 `gate=0` 的零门控 transport；
- transport 必须在真实输入上与原生 `B_release` action output 逐位一致；
- 工程链路检查使用 dev simulator seeds；正式 C0 数字只在锁定的 final-test bank 上生成。

C0 没有 training-seed 维度。不得复制同一个 checkpoint 三次后报告伪造的 training mean ± std；正式报告应提供 rollout episode 层面的置信区间。

当前用户已有原始 FastWAM 数据，因此主线直接推进 C1/C3。若将 C0 纳入 strict aggregate，必须一次提供 3 tasks × 2 domains 完整六格，并与 C1/C3 使用相同 final seed bank 和 rollout protocol；否则不纳入。

## 3. Phase C：Policy paired 数据审计

现有完整 artifact：

```text
FastWAM/outputs/policy_content_adapter/native50hz_three_task_rgb640x480_v1/full_lerobot_v21
```

其 export audit 已 PASS：600 scene episodes、50 contents/task、50 Hz、future 32-step × 14D、`all_pairs_exact=true`、无插值，paired manifest SHA 为 `57114b6541b33c0c50e0c5a777f9bed870fe2f4847863f53517e99d8e43637b1`。因此本阶段不是重新采集，而是复核并把现有 full artifact 与 `B_release` lineage、最终 state bank 和 split manifest 重新 SHA-lock。

### C1. 原生格式

不使用旧 30 Hz 数据，也不做 30→50 Hz 插值。每个样本必须包含：

```text
第一视角相机 + 左腕相机 + 右腕相机
+ 当前 robot state
+ 原生 50 Hz 状态/动作
+ future 32-step × 14-D action target
```

C、R1、R2、R3 是同一物理状态的四种场景版本，不是四个相机。每种场景版本内部都有三个同步相机。四个版本共享物理状态、robot state、时间戳和 future action target；专家只执行一次，其他版本从同一状态重渲染。

### C2. 数量

| Split | Clean/task | Random/task | Physical trajectories/task |
|---|---:|---:|---:|
| Train | 30 | 90 | 30 |
| Val | 10 | 30 | 10 |
| Test | 10 | 30 | 10 |
| 总计 | 50 | 150 | 50 |

Random 由 R1/R2/R3 均分。Train 每条轨迹固定选 8 个可覆盖完整未来 32 步、无需末端 padding 的状态，形成 240 groups/task、720 groups/三任务、2,880 views。

### C3. Gate

- 三相机身份、尺寸、帧数和时间同步正确；
- 状态/动作确为原生 50 Hz，action window 为 `[32,14]`；
- 四个 scene variants 的物理状态、robot state 和 action target 逐项一致；
- 随机化不改变接触、目标或动作有效性；
- task/trajectory/state/scene/split provenance 完整；
- Train/Val/Test 不交叉；
- state-bank manifest 和 SHA 锁定。

旧 E0–E3 数据和结果保持不变，但不进入正式 Policy 训练。

## 4. Phase D：从 `B_release` 提取 Layer-16 cache

使用锁定 SHA 的 `B_release`，对 C-phase paired 数据重新提取：

```text
policy_release50tasks_native50hz_four_scene_v1
```

必须验证：

- checkpoint/stats SHA 与 A-phase lineage 相同；
- paired manifest/state-bank SHA 相同；
- camera 顺序和 scene variant 顺序固定；
- layer=16，每个 view token shape 为 `[120,3072]`；
- 每个 physical state 恰好有 C/R1/R2/R3 四个 views；
- dtype、代码、预处理和 aggregate payload SHA 完整；
- 同一真实输入下，cache extractor 与在线 native prefill 的 Layer-16 tokens bit-exact；
- 不读取或覆盖 E0–E3 cache，也不使用未完成 `B_CR` cache。

当前 P-v1/P-v2 都冻结 Video DiT，因此这份 immutable cache 可由 C1/C3 和三个 Stage 2 seeds 共享。若后续解冻 Video DiT，当前 cache 协议立即失效。

## 5. Phase E：选择 P-v1 或 P-v2

| 模式 | Video Backbone | Head/GCA | ActionDiT |
|---|---|---|---|
| P-v1 | Frozen | Train | Frozen |
| P-v2 | Frozen | Train | 小学习率更新 |

在本阶段任何 dev rollout 前，先锁定 `lambda_ctr`、contrastive temperature、paired/official batch ratio、max steps、参数组 LR、三个正式 Stage 2 seeds 和所有候选 config SHA；这些值不得根据 dev/final 结果回写。

选择流程：

1. 从同一个 `B_release`、同一 Head/GCA 初始化和同一公共配方，使用 C1/action-only 目标（`lambda=0`）各短训一个 P-v1/P-v2 dev checkpoint；
2. 使用同一个 `dev_selection` seed bank，在三个任务的 Clean/official Random 上各评测 20 episodes/task/domain；
3. Clean macro SR 比两者最佳值低超过 0.05 的候选淘汰；
4. 合格候选中选择 official Random macro SR 更高者，完全打平固定选择 P-v1；
5. 将两个 checkpoint、dev rollouts、规则和胜者写入不可覆盖、SHA-bound selection manifest；
6. C1/C3 所有 seeds 固定使用同一胜出模式；
7. `final_test` seed bank 与 dev bank 完全不相交，且不参与模式选择。

禁止用 C3 contrastive dev 结果或 `C3-C1` dev gap 选择 P 模式。现有旧 dev-pilot 配置若使用 `lambda_contrastive>0`，必须先改写并重新审计。

旧 P-v1/P-v2 smoke 只证明工程链路可以训练和部署，没有 online SR，不能用于本次选型。

## 6. Phase F：配对训练 C1/C3

### F1. 训练目标

统一写为：

\[
L(\lambda)=L_{\text{action}}(D_{\text{official}})
+\lambda L_{\text{contrastive}}(D_{\text{paired}}).
\]

- C1：`lambda=0`；
- C3：`lambda=lambda_ctr>0`，paired stream 不提供 action loss。

Stage 2 official stream 固定使用三个目标任务各 50 Clean + 500 Official Random，共 1,650 episodes；使用 `B_release` 配套 stats。

### F2. 三个配对 seeds

正式 Stage 2 seeds 为 `[1,2,3]`。对每个 seed `i`：

1. 从同一个 `B_release` 开始；
2. 生成一份 Head/GCA 初始 state，并由 C1_i/C3_i 共同加载；
3. 保存并核对初始 tensor SHA；
4. 使用相同 official batch 顺序、action noise、diffusion timesteps 和训练步数；
5. 使用相同 optimizer、参数组 LR、scheduler、precision、global batch、gradient accumulation/clipping；
6. C1/C3 读取完全相同的 paired batch 顺序并执行相同公共 forward/随机流，C1 将 paired loss 乘零；
7. 唯一允许产生额外梯度的差异是 C3 的 paired contrastive supervision。

这三个 seeds 只覆盖 Stage 2 adapter/优化随机性，不覆盖作者预训练基座的不确定性。

### F3. Formal diff gate

C1/C3 config 使用字段 allowlist 比较。除方法名、输出路径、`lambda_ctr: 0 -> >0` 和由此必需的 contrastive-gradient 开关外，任何影响训练语义的差异都必须 fail closed。

## 7. Phase G：正式在线评测

只测 RoboTwin 官方：

- `demo_clean`；
- `demo_randomized`。

所有组锁定：相同 simulator seeds、episodes/task、instruction、action horizon、inference steps、replan 和 success definition。建议每 task、每环境 100 episodes。

主表（schema v4/profile `c1_c3_primary`）：

- C1、C3 每任务 Clean SR 和 official Random SR；
- 三任务 macro average；
- C1/C3 三个 Stage 2 seeds 的 mean ± std；
- 三个 paired `C3_i-C1_i` delta，条件允许时给 episode/seed 层面的配对区间；
- 严格记录数为 `2 × 3 × 3 × 2 = 36`；
- 同协议完整 C0 若存在，可再附加六格并报告 C3−C0；部分 C0 会被拒绝。

主表不报告 R3 success、Style/State/Ratio 或 R3→Clean R@1。`demo_randomized` 同时可能改变背景、杂物、光照和桌高，因此只声称 official Random robustness，不把增益完全归因于背景。

## 8. Phase H：后续辅助对照和消融

主结果锁定后再运行：

1. C2 Naive Aug：official action loss + paired action loss；
2. C2−C1 与 C3−C2；
3. E2 pretrained Head warm-start；
4. query 数、`lambda_ctr` 等预先定义的消融。

C2 保留原定义，不因本次基座切换而删除；它只是不再阻塞 C0/C1/C3 主线。

### Z2. Stage 1 定义

- loss：原生 `L_video + L_action`；
- 不加入 Content Head、GCA 或 contrastive；
- 作者 optimizer、LR、cosine scheduler、5 epochs；
- 8 GPUs × micro-batch 8/GPU × gradient accumulation 2；
- effective global batch 128，18,215 optimizer steps；
- 基座 seeds `[1,2,3]`。

### Z3. 后续复验

完成每个 `B_CR^(i)` 后，分别重提与其 SHA 匹配的 Layer-16 cache，再在该基座内配对运行 C1_i/C3_i。它只回答“主方法效果是否依赖作者全任务 release 初始化”。

release-base 和 `B_CR`-base 必须使用不同 setting 名称、不同 cache、不同主表和不同结论。当前已启动或部分完成的 Stage 1 run 不进入 release-base 主结果，也不根据其中间 loss 改变当前方法。

## 10. 推荐执行顺序

1. 实现并审计 `author_release` lineage；
2. 将 formal configs、cache/training/evaluation audits 改为 release ancestry；
3. 跑 C0 原生部署 gate；
4. 完成 paired 数据与 state bank 最终审计；
5. 从 `B_release` 提取四场景 Layer-16 cache；
6. 运行 P-v1/P-v2 dev pilot并锁定胜者；
7. 配对训练 C1/C3 seeds `[1,2,3]`；
8. 在独立 final-test bank 上统一评测 C1/C3，生成 36 格主矩阵；
9. 锁定主结果后运行 C2 和其他消融；
10. 资源允许时再完成 `B_CR^(1/2/3)` 及其 C1/C3 扩展复验。

## 11. 停止条件与当前状态

任一 checkpoint/stats lineage、数据频率、动作窗口、scene pairing、cache identity、初始化或公平性检查失败时，后续阶段 fail closed。Smoke 不自动启动正式训练，Pilot PASS 不等于完整实验完成。

截至 2026-08-19：新主线规划已经批准并写入文档；方法和大部分数据/训练组件可复用，但当前 active formal configs、cache extractor、C0 transport、训练审计和结果聚合仍绑定三任务 `B_CR` completion。完成 release-base lineage 与 gate 适配、更新测试并严格通过之前，不能把旧正式命令当作新主线命令，也不能宣称 C0/C1/C3 正式结果已经完成。

## 12. 2026-08-22：P-v2 ActionDiT 后续机制实验

P-v1 的 36-cell 正式结果已经锁定，继续作为主实验。新增实验在看过该结果后提出，因此明确标记为 post-hoc mechanism study：C1-P-v2 与 C3-P-v2 都训练 ActionDiT、Head 和 GCA，唯一差异仍为 `lambda_contrastive=0/0.1` 及对应 gradient。

先运行 seed 1 的 1800-step pilot。原 materialization 预留 simulator seed 53、20 episodes/task/domain；2026-08-22 在没有完整 pilot manifest、没有依据 partial 结果作决策时，用户要求统一原始 FastWAM RoboTwin 的 100-episode 规模。因此新增透明、不可覆盖的 amendment，正式 pilot 改为每个任务 Clean 100 + Official Random 100，即 600 episodes/control；旧 20-episode partial 永久标为无效。只有同时满足 Random macro `C3-C1 >= +3pp` 与 Clean macro `C3-C1 >= -3pp` 才扩展 seeds 2/3 和未打开的 seed59 确认性测试；否则停止，不做结果驱动调参。完整执行规范见 `FastWAM/docs/pv2_actiondit_followup.md`。

2026-08-22 实际 gate：Clean `+2.00 pp`、Official Random `+4.67 pp`，两项 PASS。扩展阶段现按锁定条件执行 seeds 2/3 的四个 1800-step run；通过 posttrain audit 后，六个 seed1/2/3 C1/C3 checkpoint 统一在 seed59 上各评测 600 episodes，最后生成 36 格、三 seed mean ± std 与 95% CI。
